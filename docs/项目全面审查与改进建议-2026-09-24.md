## 1. 总体判断与审查边界

### 1.1 当前项目处于什么阶段

当前工程已经超出纯 UI 骨架阶段：模型路由、对话持久化、长期记忆、流式语音、受限任务工具、Office 文件生成、活动 Office 操作、游戏动作日志和游戏插件均有实际实现。继续沿现有结构演进是合理的，没有必要为了“架构更漂亮”先整体重写。

但目前尚不能将“模块有代码”“单元测试通过”“能在真实场景稳定使用”视为同一件事。最需要解决的是跨模块链路是否闭合、异常时状态是否可信、权限判断是否精确，以及安装后是否能持续运行。

建议首个稳定版本聚焦三个可验收闭环：

- **陪伴闭环**：启动桌宠 → 明确开启监听 → 正常聊天 → 可打断 → 记忆可追溯 → 提醒可靠送达。
- **办事闭环**：输入目标 → 展示实际影响 → 执行 → 用证据核验 → 失败或重启后可解释地恢复。
- **游戏闭环**：连接具体存档 → 获取可靠状态 → 执行动作 → 验证游戏内效果 → 随时停止 → 不误称完成。

### 1.2 值得保留的已有设计

1. Python 功能按模型、记忆、语音、任务、应用、游戏、陪伴拆分，已有清晰的领域边界。

3. 模型密钥已有 Windows 凭据库实现，公开状态不直接返回聊天模型密钥。
4. 任务已有持久化、原子领取与结果不明时暂停机制，避免简单重试造成重复操作。
5. 游戏动作已有唯一 ID、观察前后状态和动作日志，屏幕聊天模式禁止发送动作。
6. 文件工具已有工作区约束、部分原子替换和读回验证；桌面新建使用独占创建。
7. 流式语音已有按完整音频片段确认的账本，方向正确，应围绕它补齐失败路径。
8. 记忆已有来源、修正记录、向量失效处理、删除关联记录和文本回退。

## 3. 优先处理的具体问题

### S01【P0／已复现】切换模型服务主机时会保留旧密钥

**位置**：`modules/models/config_store.py:146` 的 `save()`；前端 `ModelStatusPanel.tsx` 的 `save()`；模型发送逻辑位于 `modules/models/provider.py`。本节后端路径均相对 `services/runtime/src/ella_runtime/`。

**现状与触发**：前端在密钥输入框为空时省略 `api_key`。后端将 `None` 解释为保留该 slot 的旧密钥，随后保存新的 provider 和 base_url。用户从服务 A 切换到服务 B，没有输入新密钥时，下一次模型请求会向 B 使用 A 的旧密钥。

**证据**：用假凭据库和 `https://a.example`、`https://b.example` 保存两次，第二次未传密钥，读取路由后旧测试密钥仍存在。未发送网络请求。

**改进方案**：

1. 将凭据与规范化的服务 origin 或明确的提供商账户绑定，而不只绑定 `chat/action/vision/persona`。
2. 主机或端口改变时默认解除旧凭据关联，要求选择适配的新凭据。
3. 同服务只改模型名允许保留凭据；兼容代理的路径变化规则需明确。
4. 保存前展示服务主机；提供“保留当前服务密钥”“替换”“清除”三种明确行为。
5. 不将旧密钥作为参数复制到新主机配置，也不在错误提示中展示密钥。

**验收**：同主机换模型保留密钥；跨主机变更不会使用旧密钥；空字符串清除与省略字段保留语义有独立测试；后台状态只展示密钥是否存在。

### S02【P0／代码确认】普通运行时接口缺少调用方认证

**位置**：`api.py:131` 的来源中间件，任务批准／执行、文件操作、模型配置及对话读取接口；`__main__.py` 的监听地址设置。

**现状**：非 GET 请求在携带不受信任 Origin 时被拒绝，但没有 Origin 时被允许；普通 API 没有独立的访问令牌。游戏插件端点已有认证，普通桌面 API 尚未采用同等机制。

**风险条件**：默认回环监听减小了远程暴露范围，但本地可访问端口的进程仍可调用批准、运行和数据接口。如果用户将监听地址改为非回环且端口可达，没有 Origin 的网络客户端也能调用。CORS 和 Origin 校验不等价于调用方身份认证；本次没有证明任意外部网页都能读取这些接口。

**改进方案**：启动时生成桌面会话凭据，由 Tauri 安全传递给前端；HTTP 和 WebSocket 都验证凭据；游戏插件保留独立身份。默认只允许回环，非回环启动必须进入专门配置模式。对 Host、允许来源和请求体大小也做明确限制。普通身份不能自行获得超出会话授权范围的工具权限。

**验收**：缺少或错误凭据无法读取敏感记录、修改配置或批准任务；正确凭据正常工作；重启后凭据生命周期明确；非回环配置不悄悄开放完整控制接口。注意这不是用于抵御已完全控制同一用户账户的恶意软件的万能隔离。

### S03【P0／代码确认】自动执行风险分类过于宽泛

**位置**：`modules/agent/engine.py:65` 的 `is_low_risk()`；`TaskPanel.tsx` 提交时固定传 `auto_run_safe: true`。

**现状**：`browser.fill`、网页打开以及不覆盖的文件创建被统一视为可自动执行。判定主要依赖工具名和 `overwrite`，没有结合目标网址、敏感字段、文件类型或任务意图。

**风险条件**：网页输入可能触发自动保存或监听事件，即使没有点击提交；新建 `.ps1`、`.cmd` 等文件也不能只凭“不覆盖”推断为低风险。文件写入不等于脚本已经执行，但需要显示其性质。当前网页工具只允许 http/https，并不限制敏感目的站点。

**改进方案**：使用工具元数据和参数共同判定风险；区分读取、填写外部站点、创建普通文档、创建可执行内容、覆盖修改、发送／提交。计划生成与授权判断分别实现。让“生成计划”按钮明确说明是否自动执行，用户可设置默认行为。网站填写加入目的域名与字段内容预览。

**验收**：新建普通说明可按设置自动运行；填写自动保存页面、敏感字段或创建脚本进入相应确认级别；未知工具和未知字段默认不自动执行；审批内容与最终执行参数一致。

### S04【P0／代码确认】骑砍高影响动作分类没有形成授权边界

**位置**：`games/adapters/bannerlord/risk.py`、`gabs.py::available_actions()` / `apply_action()`。

**现状**：代码明确将风险等级作为元数据，PLAY 模式可执行发现的非只读工具。宣战、读档、新游戏、角色处置、作弊相关命名可能被归为高影响，但未因此限制执行。

**影响**：笼统的“开始游玩”可能覆盖用户并未预期的重大存档变化。实际可调用范围取决于当前 GABS 暴露的工具，本次未在存档里执行。

**改进方案**：将普通游玩与高影响操作分开授权；按具体存档、能力组和时间范围发放许可；明确保存／读档、作弊、重开和永久性角色改变的规则。对带有通用命令语义的工具审查真实 schema，不能只按名称或描述判定边界。

**验收**：普通游玩会话不会自行获得重开、作弊、宣战等授权；确需执行时展示具体效果；来自游戏状态或工具描述的文本不能扩大权限。

### S05【P1／代码确认】陪伴组件未挂载，提醒投递链路没有闭合

**位置**：`apps/desktop/src/features/pet/PetWindow.tsx`、`CompanionControl.tsx`、`AdminWindow.tsx`；后端 `CompanionStore.poll_events()`。

**现状**：`CompanionControl` 实现了饱腹、喂食和每 10 秒轮询事件，但未被当前窗口引用。`PetWindow` 只渲染 Live2D 和语音组件；后台提醒页负责增删设置，不承担该事件轮询。

**影响**：按当前前端入口正常启动，创建提醒不等于会收到提示；喂食入口及任务／游戏进度陪伴播报也缺少实际消费端。README 中的相关描述与调用链不一致。

**改进方案**：将事件消费移到常驻应用层，明确哪个窗口负责投递，防止双窗口竞争。桌宠可保持简洁外观，但需有可见提醒、通知中心或系统通知出口，喂食可放右键菜单。不要让关键提醒依赖用户是否打开某个后台页面。

**验收**：只启动桌宠、不打开后台时提醒可送达；双窗口不会重复；安静时段和错过提醒可追踪；喂食能从实际 UI 完成。

### S06【P1／代码确认】临时断线会清除聊天会话标识

**位置**：`apps/desktop/src/features/pet/ChatControl.tsx:25`。

**触发**：已有会话时进入聊天页，后端未启动、请求超时或任意非成功响应，统一进入 catch，删除 localStorage 的会话 ID，并清空当前消息。

**影响**：数据库中的旧会话不一定丢失，但前端入口丢失。当前也没有会话列表接口／界面帮助重新找回，因此用户会感知为历史消失。

**改进方案**：仅在明确 404 且与当前会话匹配时处理不存在状态；网络错误保留 ID 和已加载内容，提供重试。增加会话列表、新建、切换和归档；必要时客户端缓存最近消息，标明离线副本。

**验收**：后端停机后再启动，原会话自动恢复；500、超时不清除标识；确实删除的会话不会无限重试；离开页面后的旧请求不覆盖新会话。

### S07【P1／已复现】TTS 部分失败后，未播放内容被作为完整回复写入记忆

**位置**：`modules/voice/streaming.py:162` 的 `_speak()` 和 `:189` 的 `_save_if_complete()`。

**触发**：前面一个或多个句子合成成功，后续句子 TTS 失败。失败后不再增加音频 segments，但 ledger.reply 继续收集模型全文。成功音频都被确认后，`acknowledged == len(segments)` 成立，于是保存全文。

**证据**：构造“1 个已确认音频片段 + 更长的完整 reply + speech_failed”的账本，调用保存逻辑后，历史包含未合成部分。此为状态机最小复现，未调用真实语音服务。

**改进方案**：区分已生成、已合成、已播放、已显示文本四种事实。语音记忆使用已确认片段的 `heard`，未听部分放入可续播队列；纯文字回退可以保存文本，但必须标注交付方式，不能把“有文字”当成“已经听完”。覆盖首句失败、中途失败、无 TTS、播放器失败等分支。

**验收**：中途合成失败后说“继续刚才的”，能衔接未听部分；后台历史能区分文本回退与播报；没有 TTS 时不会被错误阻塞。

### S08【P1／代码确认】多个语音连接共享同一个可变会话

**位置**：`api.py::get_voice_session()` 使用缓存实例；`voice_stream()` 为每个连接创建 turn；`StreamingVoiceTurn.interrupt()` 修改共享 session。

**风险条件**：双窗口、连接重建、旧连接延迟关闭或同时调用整句接口时，多个 turn 共享 `_generation`、历史和剩余回复。generation 能阻止部分过期响应，但旧 turn 的 finally/interrupt 仍可能改变新会话。

**改进方案**：引入 voice_session_id、turn_id、owner_connection_id；所有事件、确认、打断都绑定所有者。采用显式单活会话租约或真正隔离的多会话。旧连接清理只处理自己拥有的资源。

**验收**：新连接开始后旧连接关闭，不会中断新回复；整句与流式同时请求有明确拒绝或抢占规则；迟到 ACK 不影响其他轮次。

### S09【P1／已复现】游戏状态的新旧判定依赖时间戳严格递增

**位置**：`modules/games/push_bridge.py:108`、`:123`；现有 `test_game_play.py`。

**现状**：后端接收状态时生成墙上时钟时间；等待新 telemetry 以 `stamp > after` 判断。不同更新可能获得相同时间戳，系统时间调整也会影响顺序。

**证据**：全套测试在此失败，单独重跑通过；冻结时钟连续发布不同 player 状态后，等待新状态稳定超时。首次失败的精确系统时钟条件未被当次日志完整记录，但复现证实了该判断缺陷。

**改进方案**：每个游戏连接维护递增 observation_seq；receipt 与完整 telemetry 分别带序号和 session_id。新旧顺序用序号，超时用单调时钟，展示和审计仍保留时间戳。

**验收**：时间戳相等、回拨和快速连续上报均能正确识别先后；旧连接上报不能覆盖新连接状态；测试使用可控时钟／事件而非短 sleep 赌调度。

### S10【P1／已复现】源码编辑恢复核验仅检查子串，可能误报成功

**位置**：`modules/applications/coding.py:157` 的 `ReplaceProjectTextTool.reconcile()`。

**现状**：恢复时以“old 不在文件、new 非空且在文件中”判成功。这无法证明文件等于预期修改结果；合法删除操作 `new=''` 又无法通过该条件。

**证据**：一个完全无关、但含有 new 子串且不含 old 的文件，恢复核验返回 verified=True。

**改进方案**：执行前持久化文件字节哈希与预期结果哈希；恢复时对照完整预期状态。结果不匹配就保持待核对，并展示差异。支持纯删除，不依赖 new 是否为空；为大文件使用可验证的补丁与基线版本。

**验收**：无关改写不能通过；预期删除可以通过；用户并发修改后不会误判；重启恢复无需再次写文件。

### S11【P1／代码确认】“不覆盖”检查与最终替换之间存在竞争窗口

**位置**：`applications/workspace_text.py::WorkspaceTextTool.execute()`、`applications/office_files.py::OfficeFileTool.execute()`。

**触发**：先检查目标是否存在，再生成临时文件，最终 `os.replace()`。如果检查后另一个进程创建了目标，替换仍可能覆盖它。Agent 内部串行锁不能阻止外部进程。

**改进方案**：非覆盖创建使用操作系统支持的原子拒绝覆盖策略；允许覆盖时使用执行前基线检查、临时文件和明确的冲突处理。保留现有 DesktopTextTool 的独占创建思路，但同时处理写入中断后残留文件。

**验收**：在检查与提交之间人为创建目标文件，目标保持不变且返回冲突；允许覆盖路径仍能读回验证；异常残留不会被误认为已成功交付。

### S12【P1／代码确认】部分执行前失败被归类为“执行后结果未知”

**位置**：`modules/agent/engine.py:170` 的 `_run_claimed()`。

**现状**：参数错误、目标不存在、缺依赖、权限错误等所有 Exception 都进入 NEEDS_RECONCILIATION。很多工具的 reconcile 返回 None，这类任务可能永远只显示“核对现场”。

**改进方案**：工具返回结构化错误，区分未开始、确定失败、已完成、结果未知、用户取消。执行前做参数和能力预检。只对真正可能产生副作用后失败的操作进入结果未知状态。增加修订计划、放弃步骤、取消任务和人工判定入口；人工判定必须在证据中标明来源。

**验收**：缺 Office 库提示安装依赖；不存在的文件允许修订目标；网络中断后的网页提交仍保持结果未知而不重放；用户能够结束无法恢复的任务。

### S13【P1／代码确认】编程检查命令与默认项目结构不匹配

**位置**：`applications/coding.py::RunProjectCheckTool.execute()`；根 `package.json`；Python 与 Rust 子目录。

**现状**：该工具固定在工作区根目录执行 `pnpm build` 和 `cargo check`。当前根 package.json 提供的是 `build:desktop`，Cargo.toml 在 `apps/desktop/src-tauri/`。pytest 的配置又位于后端子项目，应明确其 rootdir 与导入环境。

**改进方案**：提供项目检查注册表，为每项配置固定 argv、cwd、超时、环境和说明。不要让模型拼任意 shell。Windows 下明确 pnpm 的实际启动方式并实测 `.cmd` 解析。检查进程需要受控超时与取消。

**验收**：在干净安装环境从默认编程工作区调用每项检查，能够找到对应配置；成功、失败和工具缺失可区分；记录实际 cwd 和命令。

### S14【P1／代码确认】提醒在返回给前端之前就标为已投递

**位置**：`companion/store.py::poll_events()`。

**触发**：数据库已写 delivered_at，但 HTTP 响应丢失、窗口退出或显示失败。下次轮询不会再返回该提醒。

**改进方案**：采用 pending → leased → acknowledged 状态。返回稳定事件 ID，前端实际展示后确认；租约到期允许重投，前端按 ID 去重。区分已产生、已展示、用户已查看，按产品需求选择完成口径。

**验收**：模拟响应丢失后提醒仍可再次取得；已经确认展示的事件不重复；双窗口同时请求只取得一个有效租约；安静时段结束后明确处理积压事件。

### S15【P1／代码确认】长步骤计划无法根据前一步观察结果动态生成参数

**位置**：`agent/engine.py::plan()` / `_run_claimed()`；`browser.py` 的工具定义。

**现状**：模型一次性生成最多 12 步静态参数，执行时逐步照单调用。读取网页或文件所得 evidence 没有进入后续模型决策，也没有显式的结果引用机制。

**影响**：对未知网页先读后填、读取代码哈希后精确修改等任务，后续参数容易靠猜。步骤都有结果不代表完成了原始目标。

**改进方案**：支持受约束的观察—决策—执行循环，或声明式结果引用。动态规划仍受原授权边界限制；参数或风险变化时重新授权。增加目标级终验，不只统计步骤成功。

**验收**：未知页面的填写目标来自实际观察；文件修改使用刚读取的版本；模型不能通过重新规划扩大路径、网站或动作范围；最终给出与用户目标对应的成果。

### S16【P1／代码确认】游戏可以仅凭模型返回 done 就标为完成

**位置**：`games/play.py::_run()` / `_decide()`。

**现状**：decision.done 为 true 时直接 completed，没有独立检查目标达成。动作目录超过 30 项时，第一阶段选择调用只传 goal、step、actions，连 visible_state 都未传入，却允许 done。

**改进方案**：让模型提出“完成候选”，由目标核验器依据最新状态判定；无法机器判断时标为待用户确认。大目录选择阶段也应携带压缩后的状态和当前子目标。区分成功、无法判断、主动停止、步数耗尽。

**验收**：目标未完成但模型返回 done 时不显示成功；大目录和小目录具有一致的目标核验要求；完成记录包含实际状态证据。

### S17【P1／代码确认】后台状态将“配置存在”展示成“可用”

**位置**：`models/settings.py::ProviderConfig.configured`、`voice/provider.py::VoiceSettings`、`VoicePanel.tsx`。

**现状**：configured、can_transcribe 和 can_speak 主要校验字段与地址形态，并未发起能力探测。前端却将其显示为可用。

**改进方案**：分开 configured、last_probe_result、reachable、capabilities、last_success_at。探测由用户主动触发或低频执行，明确是否产生供应商费用；探测失败保留配置但提示原因。

**验收**：错误模型名、错误密钥、网络离线均不会显示“已验证可用”；无 TTS 与 TTS 故障提示不同；保存配置后不谎称实际请求成功。

### S18【P1／代码确认】运行时没有完整的桌面启动与退出托管

**位置**：Tauri `main.rs`、`tauri.conf.json`、Python `__main__.py` 与 README 启动说明。

**现状**：桌面端和 Python 运行时需分别启动；Tauri 未见运行时 sidecar 启停与健康握手，打包配置也未体现后端可执行资源。关闭后台窗口后的重新打开策略、托盘和单实例处理需补齐并实测。

**改进方案**：由桌面进程托管运行时生命周期，或明确安装独立本地服务。启动时健康握手和版本检查，端口冲突给出诊断；退出时处理浏览器、游戏连接、语音与未完成任务。后台关闭优先隐藏，避免快捷键找不到已销毁窗口。

**验收**：全新账户只启动一个入口即可使用；退出没有孤儿运行时；重复启动行为一致；后台关闭再打开正常；故障时用户无需猜测 Python 命令。

## 4. 运行时与接口架构

### A01【P2／工程建议】拆分集中式 API 装配文件

**依据**：当前 `api.py` 约 1,164 行，集中包含路由、请求模型、依赖构建、游戏启动、语音协议处理和事件调度。模块目录已经拆分，API 层仍是主要耦合点。

**方案**：按 chat、models、memory、voice、tasks、games、companion 建立 APIRouter；把依赖装配放在单独容器或工厂中。接口层只做校验、调用服务和响应转换。保留现有 URL，避免为重构制造前端迁移负担。

**验收**：每组路由能用替代服务独立测试；添加一种应用工具不需要同时修改多个无关路由；无业务模块反向依赖 API。

### A02【P1／代码确认】补齐运行时资源生命周期与初始化失败隔离

**依据**：多个服务由 lru_cache 首次请求时创建，未见统一 lifespan 管理。`BrowserSession.close()` 已存在，但 API 未集中在 shutdown 中调用。Agent 构造还会初始化 DesktopTextTool；平台或桌面路径不可用可能拖累整个任务模块。

**方案**：用应用生命周期管理模型 HTTP 客户端、浏览器、语音意图任务、游戏任务与适配器。工具能力延迟初始化并独立报告 unavailable；初始化失败不能让只读任务列表也不可用。退出按“停止接收新任务 → 标记未完成状态 → 取消并等待后台工作 → 释放资源”执行。

**验收**：没有 Office、没有桌面目录权限、浏览器启动失败时，聊天和其他工具仍可用；关闭应用后无遗留任务、浏览器句柄或未收集异常。

### A03【P1／待实测风险】异步路径中的同步数据库和文件 I/O 可能阻塞其他请求

**依据**：异步路由和模型／语音调用链中直接使用同步 sqlite3；部分 Office 文件创建、源码读写和遍历也在 async 方法内同步执行。当前 SQLite 超时多为 5 秒。

**方案**：先量测事件循环延迟，再将重 I/O 放入有界工作线程或统一异步存储层。数据库繁忙采用可控重试和短事务；不要简单给每个调用无限创建线程。限制文件大小、目录扫描量和同时运行的任务数。

**验收**：在数据库锁竞争、Office 生成和聊天并发时，语音打断和健康检查仍能及时响应；记录 P95 延迟和排队时间，不只测单请求。

### A04【P1／代码确认】长任务应脱离单次 HTTP 响应生命周期

**依据**：普通任务 run 接口直接 await 整个任务；聊天摘要也在响应返回前等待。客户端断线后是否取消、继续或重试的语义没有统一约定。

**方案**：执行接口返回任务 ID 与已受理状态，后台 worker 更新持久状态；前端订阅事件或轮询。增加请求幂等键和执行租约，防止响应丢失后再提交造成重复工作。客户端关闭不等于用户取消，取消应有独立指令。

**验收**：执行中关闭／刷新页面后可重新查看同一任务；网络重试不创建重复副作用；取消与断线状态有明确区别。

### A05【P2／工程建议】统一错误契约、日志与链路标识

**依据**：前端对 HTTP 错误、字符串 detail、校验错误数组的处理不一致；后端部分错误只留下异常类型，难以判断失败步骤。

**方案**：标准错误字段包含 code、message、retryable、request_id、task_id、step_id；详细堆栈只进入本地诊断日志。贯通聊天、ASR、模型、TTS、记忆摘要和动作执行的关联 ID。日志默认不保存密钥、完整音频、全文对话或表单值。

**验收**：用户能复制一个诊断编号定位错误；错误页面给出下一步；导出诊断包有可预览内容与脱敏规则；不要以脱敏为由只保留毫无帮助的“失败”。

### A06【P1／代码确认】统一接口资源上限与输入契约

**依据**：部分请求已有字符／音频限制，但 PluginState 和 PluginReceipt 使用宽泛字典；状态大小校验在 JSON 解析后进行，receipt 未见同等大小约束；memory 的 limit 接口未声明清晰范围；WebSocket feed 的 ValueError 不在命令解析异常处理范围内。

**方案**：从 HTTP／WebSocket 消息入口限制总大小、深度、频率和连接数，再做领域 schema 校验。为分页、排序、时间范围提供上限。WebSocket 二进制音频错误应返回结构化错误并正确关闭，不能依赖未捕获异常终止连接。

**验收**：超长消息、奇数字节 PCM、超过 60 秒录音、过深 JSON、过大 receipt 都得到明确错误；服务不会因一个坏输入占用无界内存或产生大量堆栈。

## 5. 模型路由人格与用量

### M01【P1／代码确认】统一所有配置入口的 URL 安全与脱敏规则

**依据**：ModelConfigInput 对远程 HTTP、URL 凭据、query、fragment 有校验，但环境变量生成的 ProviderConfig、VoiceSettings 和 EmbeddingSettings 的规则不同。语音 public_status 直接返回 base_url。

**方案**：抽取共用端点验证器，环境变量与 UI 使用同一套规则；远程传输和本地端点分别定义。公开状态始终使用去凭据、去敏感 query 的 URL。语音、embedding 和 Fish 配置均进入相同审查范围。

**验收**：从环境变量填写远程明文地址不会绕过 UI 约束；带凭据或敏感 query 的地址不出现在状态响应和日志；IPv4、IPv6、本机主机名行为一致。

### M02【P1／代码确认】配置保存需要处理凭据库与 SQLite 的部分成功

**依据**：保存先更新凭据，再写 SQLite；重置先删除 SQLite override，再删除凭据。这两类存储无法靠一个 SQLite 事务同时提交。

**方案**：引入配置版本和明确的提交阶段，写失败时回滚关联或保留可修复状态；避免“返回失败但路由已经变了”无法解释。路由切换使用一次请求内的配置快照，避免主模型生成和人格润色分别读到不一致的版本。

**验收**：模拟凭据写失败、数据库只读、重置时凭据库不可用，最终配置状态均可查询和修复；旧密钥不会错误关联到新地址。

### M03【P2／工程建议】按供应商能力处理流式、结构化输出与错误

**依据**：当前统一通过兼容 Chat Completions 调用，固定传 max_tokens 和 stream_options；操作计划主要依赖提示词要求 JSON。不同端点的实际兼容情况本次未进行外部验证。

**方案**：为已验收的供应商记录 capabilities，包括流式用量、结构化输出、视觉、输出限制和错误形态；支持严格 schema 时启用，未支持时做本地校验。无效 JSON 允许有限次格式修复，但不允许顺便改变已授权操作。

**验收**：受支持端点的样本响应均有契约测试；不支持的参数不会导致无意义重试；解析失败向用户说明是哪一层失败。

### M04【P2／代码确认】请求超时、重试与连接池需要分层设计

**依据**：模型传输通常为每次请求新建 AsyncClient，使用固定超时；未见统一的退避和熔断策略。相同模型服务可能被聊天、记忆、游戏并发调用。

**方案**：运行时复用客户端；区分连接超时、首字超时、流中空闲超时和总预算。对限流和短暂故障有限退避，避免自动重试可能导致额外计费的已受理请求而不记录。按供应商限制并发，取消应传递到下游。

**验收**：429、503、网络中断、半途流断开有不同结果；重试次数和原因可见；停止任务后没有继续生成大段无人使用的输出。

### M05【P1／代码确认】上下文按消息条数裁剪，缺少 Token 预算

**依据**：文字聊天默认最近 20 条消息，语音保留 12 条；单条用户文字可达 10,000 字符，还会加入人格与最多 5 条记忆。

**方案**：根据具体模型上下文能力，给系统提示、历史、记忆、工具结果和输出预留预算。优先保留近期指令、关键约束、未完成任务与来源；历史摘要不是无限追加。明显超长输入在请求前分块或提示。

**验收**：多轮长文本不会突然超上下文；删减策略不会丢掉用户刚明确提出的约束；实际／估算 Token 口径分开。

### M06【P2／代码确认】人格润色与随机回复长度需要可控

**依据**：非操作请求可随机选择长短；普通聊天可增加第二次人格模型调用，流式语音不走同一润色路径。

**方案**：默认长度由对话场景和用户偏好决定，随机只用于低影响表达。让人格润色可关闭，记录额外耗时；事实、数字、路径、任务状态和承诺不得在润色时发生变化。为文字与语音建立同一组人格回归样例。

**验收**：短答偏好持续生效；工具结果不会被润色成“已经完成”但实际未完成；润色服务不可用时仍快速返回主回复；分别记录两个模型的用量。

### M07【P1／代码确认】用量账本没有覆盖全部模型成本路径

**依据**：非流式调用失败前不会进入成功后的 record；stream_voice 在 finally 中记录未知用量，处理不同。EmbeddingProvider 没接入 UsageStore。部分语音调用缺少 task_id；记忆摘要和游戏决策复用 action 用途。

**方案**：统一记录每次请求尝试，区分成功、失败、取消、用量未知、重试；新增 operation 字段区分聊天、润色、摘要、embedding、ASR、TTS、游戏决策。用会话和请求 ID 串起来。音频时长、字符量等单位与 Token 分列，不换算成伪装的实际 Token。

**验收**：失败调用仍可查到，但未知消耗不记为零；embedding 和润色可单独查看；同一轮语音能汇总所有子调用；不向用户宣称账本等于供应商最终账单。

### M08【P2／代码确认】用量日期筛选和分组存在规模限制

**依据**：UsageStore 对时间字段使用 substr 按日期过滤；分组最多 200 行，接口未提供继续翻页；部分计数缺失时只汇总输入与输出都已知的请求。

**方案**：统一 UTC 存储与用户时区展示，用明确时间范围查询；为请求、模型、用途和时间范围建立合适索引。提供分页、导出和完整性说明；已知输入／未知输出可分别统计，而非丢掉已知部分。

**验收**：跨午夜、跨时区日期筛选一致；分组超过 200 仍能看到全部；“已知消耗”“未知请求数”“估算费用”定义清晰。

## 6. 长期记忆与对话数据

### D01【P1／代码确认】文字聊天摘要失败缺少持久补偿

**依据**：ConversationService 在消息数为 16 的倍数时直接 await 摘要；文字路径未像 VoiceHistory 一样使用持久 summary window 补偿。失败返回 None 后，下轮不会自动补该窗口。

**方案**：文字与语音统一摘要任务表，以 conversation_id 和消息范围唯一标识；主回复先返回，摘要后台处理并有限重试。将来源检查与写入完成状态分离，避免“只写了一条就认为整个窗口完成”。

**验收**：第 8 轮摘要故障不会拖慢或丢失聊天；重启后能补做；同窗口重试不生成重复记录；用户删除对话后未完成摘要不再重新写入。

### D02【P1／代码确认】记忆检索和导出存在不一致的数量边界

**依据**：MemoryStore.search_hybrid 遍历最多 10,000 条 memory_items，最后最多返回 20 条；API 列表默认 limit=100，但带搜索词时仍受搜索上限影响。向量读取则可能扫描该模型的全部向量。

**方案**：把 UI 搜索与模型召回分开接口；UI 搜索分页，模型召回保持小 top-k。先由索引选候选再评分，避免每轮全表 Python 计算。超过容量时显示明确状态，不能静默让旧记忆失去可检索性。

**验收**：超过 10,000 条后仍能在 UI 找到旧记录；分页无重复遗漏；模型 top-k 与 UI 页大小互不干扰；检索耗时可量测。

### D03【P2／代码确认】向量索引建立放在用户聊天关键路径

**依据**：HybridMemoryRetriever.search_async 先 index_missing，再请求 query embedding。首次索引最多 20 条，每轮可能需要两次远程向量调用。

**方案**：新增或修改记忆时进入后台索引队列，聊天优先使用已建立索引及文本回退。为查询向量做小容量缓存；索引记录 provider、endpoint 指纹、model、dimension 和 revision，不能只以模型名判断向量兼容。

**验收**：大量新记忆不会显著拖慢首字；同名但不同服务的向量不混算；模型切换可渐进重建；索引故障不阻止文字聊天。

### D04【P1／待实测风险】删除与重新提取之间需要防止“忘掉后又记起”

**依据**：记忆删除会删除关联向量和修正记录，这是优点；但原始对话独立保留，摘要、明确记忆捕获和未来重新处理仍可能产生同内容记录。已有“记忆删除不等于删除聊天”的文档提示应保留。

**方案**：提供删除单条记忆、删除来源对话、删除会话派生记忆、暂不提取该主题等不同操作。对用户明确要求遗忘的内容，可以用最小化的抑制标记阻止重新导入，但不要为了抑制而完整保留被删除的敏感正文。处理进行中的摘要和向量写入竞态。

**验收**：删除与摘要并发时不会重新出现同条；用户能了解删除范围；备份恢复后的遗忘语义明确；不将 SQLite secure_delete 宣称为所有设备和备份上的绝对不可恢复。

### D05【P2／代码确认】自动记忆识别规则需要事实更新与否定处理

**依据**：MemoryCapture 使用句首正则及关键词分类，重复检测只做内容 casefold；置信度固定。日期、喜好变化、引用和条件句的语义无法仅靠这些规则准确处理。

**方案**：明确命令可直接记录，自动偏好先作为候选；引入实体、属性、生效时间和 supersedes 关系。用户说“现在不喜欢 X 了”应更新原偏好，而不是长期并列召回两条冲突事实。展示提取理由与来源。

**验收**：否定、引用、玩笑、假设、第三人称不误写为用户事实；偏好更新优先于过期记录；允许用户关闭自动提取而保留手动记忆。

### D06【P2／代码确认】修正后的来源查看体验不完整

**依据**：MemoryStore.correct 将 source_type 改为 manual、source_ref 清空，原始来源保存在 revisions。memory_source 接口只接受当前 conversation 来源，UI 不容易直接回到原始对话。

**方案**：分开“原始来源”和“最后修改来源”；增加修正历史查询。修正卡片展示原文、修改理由、时间和原始消息范围；显示可信度来源，不把固定 0.7 当成真实统计概率。

**验收**：人工修正后仍可追溯最初依据；删除来源后有明确提示；导出与界面看到的修正历史一致。

### D07【P1／工程建议】为多 SQLite 数据库建立版本迁移与备份恢复

**依据**：模型、记忆、对话、用量、任务、游戏日志和陪伴数据分散存储，主要通过 CREATE TABLE IF NOT EXISTS 初始化，未见统一迁移与恢复流程。

**方案**：每个库有 schema_version 和逐版迁移；升级前一致性备份，恢复前校验格式。跨库关系采用明确的应用级一致性规则，不强行把全部库合并。配置和密钥的备份策略分开，备份不得默认包含可直接使用的明文凭据。

**验收**：旧版数据可升级；升级中断可回退；备份恢复后会话和来源关联正常；磁盘满、损坏库不会使整个应用无提示崩溃。

### D08【P2／工程建议】增加记忆质量评估而不只测试 CRUD

**方案**：建立固定中文样例集，覆盖生日、地点、偏好更新、同义表达、时间变化、名字相似、矛盾事实及删除。分别评估提取准确率、召回相关性、过期事实率与来源正确率；不要只看“返回了五条记忆”。

**验收**：检索权重、阈值或 embedding 更换前后有可对照报告；错误记忆可定位到提取或召回环节；质量集不使用未授权的真实隐私对话。

## 7. 语音交互

### V01【P1／代码确认】连续监听默认开启，但可见状态不足

**依据**：continuous 使用 localStorage 值不等于 false 即开启；服务配置后可自动开始。voice.css 隐藏按钮，主要状态文本为 sr-only，正常语音情况下没有持续可见的状态指示。

**方案**：首次使用明确选择监听模式；在桌宠旁或托盘持续显示麦克风状态，提供一键静音。区分监听、正在上传、思考、播放和断线。保持角色外观简洁时，也应有低干扰的状态点和展开入口。

**验收**：用户无需听见声音就知道是否正在监听；禁用后不会因重连自动开启；服务未配置、权限拒绝和设备不可用都能看到原因。

### V02【P1／代码确认】断线处理不等于完整重连机制

**依据**：WebSocket onclose 停止录音并设置 idle，但没有统一退避重连；连接等待 Promise 没有明确超时和关闭拒绝处理；事件回调没有全部执行 generation 校验。

**方案**：将连接状态机独立为 hook／服务，增加连接超时、有界指数退避和网络恢复触发。每个回调核验连接与 turn 身份；断线时清理播放队列、Object URL、麦克风和旧定时器。明确是否续传，首版可选择断线后重新录音但不重复提交旧内容。

**验收**：启动失败不永远卡在“连接中”；运行时重启后可恢复；旧连接消息不串入新回复；不因错误持续重试而无限调用收费接口。

### V03【P2／代码确认】累计音频重复转写放大延迟和消耗

**依据**：后端每增加约 2 秒录音可上传累计 PCM 进行临时转写，结束后再上传全文。若 60 秒持续录音且服务足够快，理想化累计上传量为 2+4+…+60，再加最终 60 秒，约等于 990 秒音频；实际次数受服务响应速度及前端自动结束影响，不能把这个上界当作实测账单。

**方案**：优先接入真正增量 ASR；否则用分块加重叠并合并结果，或降低 partial 频率。UI 将临时识别与最终识别区分，费用记录实际请求次数和音频秒数。

**验收**：长句识别不会重复插入词语；临时结果不触发任务／记忆副作用；相同输入的上传量和端到端耗时可对比。

### V04【P2／代码确认】PCM 重采样为抽样，缺少抗混叠处理

**依据**：pcm-worklet.js 通过位置累加选择样本转为 16kHz，没有滤波或插值。

**方案**：使用经过验证的重采样实现，并覆盖常见 44.1kHz、48kHz 输入。保持 AudioWorklet 实时线程工作量可控，避免每个回调创建过多对象。记录实际输入采样率和输出时长以定位问题。

**验收**：不同设备输入均生成正确时长的 16kHz 单声道 PCM；测试音频无明显频率失真和丢样；真实中文识别质量有对比。

### V05【P1／待实测风险】固定音量门限和短静音阈值影响长句与轻声识别

**依据**：前端 RMS 阈值 0.014、约 900ms 静音提交、约 18 秒自动结束；无设备校准。回声、键盘声、呼吸和小声讲话的实机表现尚未验证。

**方案**：允许灵敏度与停顿时长设置，增加起止迟滞；可采用更可靠的 VAD。超过录音上限先明确提示，不悄悄截断。播放时如要支持自然插话，需在回声消除基础上单独设计，不应把按钮打断宣传成自然全双工。

**验收**：安静环境、风扇声、轻声、长停顿和外放都各测；连续多轮不自言自语；语句被分段时用户能看见并继续。

### V06【P2／代码确认】模型流与逐句 TTS 串行等待

**依据**：StreamingVoiceTurn 在遍历模型 delta 时 await `_speak()`，每遇到一句便等待 TTS；句子正则不含英文句点，英文长回复可能直到末尾才合成。

**方案**：使用有界生成队列与 TTS worker，让读模型流、分句和合成适度并行；播放顺序仍严格按 index。中文、英文、数字小数与代码分句分别处理。队列满时施加背压，取消能同时停止生产者和消费者。

**验收**：首个音频延迟降低；长回复队列不无界增长；英文能分句；打断后不会继续合成大量排队句子。

### V07【P1／代码确认】整句模式与流式模式的产品描述不一致

**依据**：后端仍保留 `/api/voice/turn`；当前 VoiceControl 只返回 StreamingVoiceControl，后台 VoicePanel 未提供整句切换。README 声称可切到原整句方式，与现有 UI 不一致。整句会话内部还通过播放比例估算听到的文本边界，不具备流式片段 ACK 的同等精度。

**方案**：明确是否保留两种模式。保留则提供选择与一致的历史语义，比例推断必须标注为估计；不保留则删除过期描述并逐步缩小维护面。优先统一状态机而不是保留两套长期分叉逻辑。

**验收**：文档描述的入口确实存在；切模式不会丢历史或重复录音；未完整听到的句子不被当成可靠听完记录。

### V08【P2／工程建议】建立语音专项性能和稳定性基线

**方案**：记录录音结束到最终识别、模型首字、首段音频、总回复时间、打断延迟、重连时间与峰值队列长度。用固定音频回放做自动化，再以麦克风和扬声器实机验证。至少包含 30 分钟连续会话和重复启停测试。

**验收**：报告有输入设备、采样率、模型、网络和机器配置；明确哪些延迟来自本机、模型或 TTS；测试后没有未停止的 MediaStreamTrack、连接或音频资源。

## 8. 任务 Agent 与应用操作

### T01【P1／代码确认】工具参数应在计划阶段完整验证

**依据**：AgentTool 主要提供 name、description、execute、reconcile；计划校验只确认工具存在和 arguments 是字典，各工具运行时才分别验证参数。

**方案**：每个工具公开 Pydantic 参数模型或 JSON Schema，以及只读性、作用目标、前置条件、幂等语义和恢复能力。计划保存前全部校验；返回字段级错误，模型可有限修正。schema 对额外字段采取明确策略。

**验收**：不存在的参数、错误类型、越界范围不会等到真实工具运行才发现；审批界面展示的是规范化后、实际执行的参数。

### T02【P1／代码确认】任务状态机缺少取消、超时与修订

**依据**：TaskState 没有 cancelled、paused 等状态；运行使用全局 `_run_lock`；没有每步统一超时。一个慢工具可能阻塞所有后续任务。

**方案**：增加排队、取消请求、已取消、超时和人工核对状态；按资源互斥而不是所有任务共用一个无限等待锁。相同浏览器或工作簿仍应串行；不同只读任务可有限并行。计划版本与审批绑定，编辑后旧批准失效。

**验收**：排队任务能取消；运行中可停止未来步骤；不能中断的 COM 操作明确显示正在等待安全结束；修改计划后必须按新影响重新判断授权。

### T03【P1／代码确认】源码写入应保留字节格式并原子提交

**依据**：ReplaceProjectTextTool 用 read_text 读取再 write_text 写入。文本读取的换行规范化可能把原 CRLF 改为 LF；写入并非原子替换，且原内容哈希可选。

**方案**：对源码编辑保存字节级基线，识别并保留换行和 BOM；必须绑定预期旧版本。生成临时文件、核验后原子替换；保留可撤销补丁。写回失败需要能判断是否部分写入。

**验收**：只改一个片段时其余字节不变；CRLF、UTF-8 BOM 文件不出现整文件差异；模拟写入中断不会留下截断源码。

### T04【P1／待实测风险】工作区约束需要覆盖 Windows 特殊路径与敏感文件

**依据**：路径 resolve 与 is_relative_to 已防止基本越界，但源码白名单不是敏感信息过滤器；JSON/YAML 中仍可能含凭据。跳过目录主要用于列举，直接 read_file 不等于具有同样排除规则。

**方案**：建立工作区敏感文件策略和最小读取权限，覆盖 junction、符号链接、设备名、NTFS 备用数据流及操作前后路径变化。不要自动遍历用户主目录。读取工具结果进入日志或模型前按用途处理敏感内容。

**验收**：临时测试工作区中的链接、保留名和敏感配置有明确结果；不得访问工作区外；用户可对被排除文件进行单次明确授权。本次未声称已经复现路径逃逸。

### T05【P1／代码确认】受限命令名不能替代执行隔离

**依据**：code.run_check 仅允许固定命令，这是必要约束；但 pytest、pnpm build、cargo check 会执行项目自己的测试、脚本或构建逻辑。

**方案**：将“检查命令”如实视为执行工作区代码。区分自有可信项目和陌生项目；为检查进程设置受控 cwd、环境、时间和资源，避免继承不必要密钥。收集子进程并支持终止，不把命令名白名单描述成完整沙箱。

**验收**：检查不会继承无关 API 密钥；超时能处理进程树；外部项目在首次执行前明确说明影响；依旧禁止模型传入任意 shell 字符串。

### T06【P2／代码确认】Git 审查证据不完整

**依据**：GitReviewTool 读取 status 和 `git diff --`，未展示 staged diff；输出只保留尾部且没有完整截断说明。

**方案**：分别展示暂存、未暂存、未跟踪文件概况，使用受控 diff 参数并避免外部 diff 程序；按文件分页并明确截断。仓库所有权异常给出诊断，不自动修改全局 safe.directory。审查不应顺便提交。

**验收**：只有暂存修改也能看到差异；大 diff 明确显示省略量；二进制和重命名有摘要；非仓库与权限错误可区分。

### T07【P1／代码确认】浏览器点击核验可能把既有页面状态当作点击效果

**依据**：BrowserClickTool 在点击后检查 expected_text 可见或 URL 相等；如果这些条件点击前就成立，点击未产生预期业务变化也可能通过。选择器使用 `.first`，页面有多个匹配项时会静默选首个。

**方案**：执行前记录基线，要求目标唯一且可见；核验业务变化而不仅是存在某段文字。例如比较状态字段、记录 ID 或成功回执。高影响提交需保存可追溯证据。导航、弹窗、新 tab 与异步刷新分别处理。

**验收**：按钮无效但页面早已有成功文字时不能通过；多个匹配目标要求重新定位；点击成功但响应丢失时不再次提交；页面导航后可跟踪正确 tab。

### T08【P1／代码确认】Office 恢复核验未证明保存到磁盘

**依据**：Excel 和 Word execute 可选择 save，但 reconcile 主要检查当前内存内容，未确认 save=true 要求是否已落盘。目标匹配主要用文档名称。

**方案**：证据分为内存修改已验证、保存成功、磁盘内容已验证。需要保存时核对 FullName 和持久状态；同名不同路径的文档不可混淆。执行前基线必填或由读取工具自动生成；按文档实例串行控制。

**验收**：内存改成功但保存失败不会标整个目标完成；同名工作簿不误改；重启核对不修改文档；保存位置和文件版本可追溯。

### T09【P1／待实测风险】Word 查找替换依赖交互式 Find 的遗留设置

**依据**：调用 `finder.Execute(FindText=old, ReplaceWith=new, Replace=2)` 未显式设置大小写、全词、通配符、格式和查找范围等选项。用户界面的 Find 设置可能影响实际匹配。

**方案**：明确初始化所有匹配参数，采用与前置 count 检查一致的精确匹配语义；处理页眉页脚、文本框和表格是否属于范围。对富格式段落保留格式策略；不能只根据新旧词数量判断业务内容完全正确。

**验收**：用户预先打开通配符或格式查找后，工具仍按声明工作；只改变指定范围；替换前后差异可复核。

### T10【P2／代码确认】Office 文件核验只检查文本／单元格，没有检查呈现效果

**依据**：当前 Word 校验段落文本、PPT 校验标题和 bullet、Excel 校验值与公式字符串。缺少分页、溢出、可读性和公式实际计算验证。

**方案**：按产物复杂度增加文档渲染和视觉检查；PPT 限制每页字数与字体下限；Word 配置中文字体、段落、标题层级；Excel 区分普通文本和公式，增加数字格式、自动筛选与必要计算校验。提供结果预览与打开文件入口。

**验收**：长中文段落和多行表格不越界；PPT 不以可打开代替可读；公式字符串正确与计算值正确分别记录；简单文件生成仍保持轻量。

## 9. 游戏能力

### G01【P1／代码确认】游戏连接需要 session 与序号，避免多实例和乱序覆盖

**依据**：PushGameBridge 每种游戏只有一个 snapshot 和 token，client_id 属于状态字段，没有在动作领取、上报和 receipt 上形成连接所有权校验。状态以接收时刻作为 captured_at。

**方案**：握手返回 connection_id、session_id、world_id 和 lease；每条完整状态含 tick／sequence 与采样时间，receipt 绑定同一会话。拒绝旧序号，失去租约的实例不可领取命令。区分接收新鲜度和实际游戏状态新鲜度。

**验收**：同游戏开两个实例不会串命令；延迟上报不会回滚状态；换存档后旧动作被拒绝；保留插件版本和能力信息。

### G02【P1／代码确认】超时、停止与结果未知需要可恢复协议

**依据**：命令仅发出一次、超时不重放，是合理保守策略；但领取响应丢失、receipt 迟到或运行时重启后，内存中的 inflight 与游玩 session 缺少完整恢复信息。取消后台协程也不等于游戏内动作已经停止。

**方案**：持久化动作生命周期和游玩会话；插件提供按 action_id 查询结果、停止当前动作和释放输入的控制通道。对领取、接受、执行、完成、回执分别定义状态。继续游玩前核对上一不明动作，不能只是换一个 ID 开始新的控制循环。

**验收**：领取响应丢失不重复执行；晚到回执可对账；点击停止后游戏释放输入；运行时重启后提示现场核对，不自动续做不明动作。

### G03【P1／代码确认】动作效果需要比“状态变化”更具体

**依据**：Minecraft 对移动主要比较水平位移；星露谷 use_tool 主要看体力降低。这些是有用信号，但未证明目标方向、目标格子或目标对象正确。PushGameBridge 主要信任插件的 verified 回执。

**方案**：按动作定义前置与后置条件：方向位移、目标方块消失及掉落、指定格子浇水状态、目标实体受伤、目标物品数量变化等。回执附结构化证据，后端检查其与请求一致。允许“动作发出但未生效”而不是强行成功。

**验收**：撞墙、击空、工具用错位置、被游戏规则拒绝时返回未生效；成功动作包含目标对象和变化前后值；不同游戏 tick 延迟有合理等待窗口。

### G04【P2／代码确认】游戏规划缺少持续进展度量

**依据**：GamePlaySession 虽保存 history，普通决策上下文主要含当前状态与 last_result，没有充分使用历史动作序列；step_limit 控制总步数，却不一定阻止无效来回移动。

**方案**：引入子目标、最近动作摘要和可观测进展指标；检测重复状态、往返动作与连续无效动作。模型只做高层决策，路径规划和短程移动交给确定性逻辑。停滞后解释原因并请求调整目标。

**验收**：被障碍物挡住不会连续浪费几十次模型调用；能说清缺少工具、距离不够还是状态不完整；每个子目标有阶段证据。

### G05【P2／代码确认】游戏日志大小与模型状态输入应分开控制

**依据**：动作保存前后快照；GABS 状态可能包含较大动作目录；模型状态超过 12,000 字符时直接截取序列化文本。长时间游玩会积累大量重复数据。

**方案**：日志存快照引用或增量，保留关键完整检查点；模型只接收按字段压缩的相关状态，避免字符串硬截断破坏语义。动作目录缓存版本化并按目标筛选。设置留存、导出和诊断容量。

**验收**：连续数小时游玩磁盘增量有上限与说明；日志仍能还原关键事件；状态截断不丢失血量、位置、目标和权限约束。

### G06【P1／代码确认】三款游戏的验收应围绕真实任务而非仅编译

**依据**：README 已声明尚需真实存档连续验收；Minecraft 当前动作目录缺少完整背包／制作流程，星露谷能力以基础移动与交互为主。

**方案**：每款固定游戏版本、模组版本、测试存档和目标脚本。Minecraft：走到目标、采集、确认背包、按目标制作；星露谷：走到农田、选择工具、完成指定交互并验证地块；骑砍：地图移动、事件选项、战斗控制及停止。若当前工具不支持某环节，标“能力待实现”。

**验收**：每款独立给出视频／状态日志／结果证据和失败清单；禁止用屏幕问答通过替代真实操作验收；测试前使用可恢复的测试存档。

### G07【P2／代码确认】游戏插件地址发现和故障日志需要统一

**依据**：两类插件读取 token 配置后使用固定 `http://127.0.0.1:8766`；后端允许通过环境变量改端口。插件中有多处吞掉网络异常，排查时信息不足。

**方案**：握手配置包含实际端点、协议版本和令牌标识，原子发布；异常日志限频记录错误类型、响应码、最后成功时间与重试状态，不打印 token。构建版本从统一来源生成。

**验收**：端口改变后插件可重新发现；错误令牌、版本不兼容和运行时离线可区分；不会每帧刷日志；日志不含凭据。

### G08【P2／工程建议】屏幕陪聊应明确观察范围与刷新方式

**依据**：当前实现为前台标题匹配的按需截图问答，已有图片尺寸和格式限制。它不等于连续视觉流或游戏控制。

**方案**：首次明确选择窗口并预览截图范围，后续绑定窗口身份而不是只依赖标题；窗口变更、遮挡、失焦时暂停。未来持续观察按变化率采样和预算限制，给出最后观察时间，避免用旧图描述当前状态。

**验收**：目标窗口变化不会截取无关窗口；用户能知道哪些画面会发送到配置的模型；旧截图的回答明确时间；屏幕模式始终没有动作执行权限。

## 10. 前端桌宠与陪伴体验

### U01【P1／代码确认】统一运行时地址与跨窗口设置

**依据**：多个组件硬编码 127.0.0.1:8766，WebSocket 单独硬编码；后端、插件和前端配置口径不一致。监听偏好依赖 localStorage 与 storage 事件。

**方案**：建立 runtime client，由启动握手返回 API 地址和会话身份；统一 HTTP、WebSocket、错误处理和超时。跨窗口偏好通过明确事件或持久设置服务同步，同窗口更新也发送本地事件。业务组件不再自己拼完整主机地址。

**验收**：换端口只改一个来源；浏览器开发与 Tauri 打包环境都可用；双窗口开关监听即时一致；重启后设置保留。

### U02【P1／代码确认】请求需要取消与过期响应保护

**依据**：多个 useEffect 请求没有统一 AbortController；切页、切模型 slot 或切会话时，迟到结果可能更新旧状态。部分轮询依赖 setInterval，不判断上次请求是否完成。

**方案**：统一请求层支持取消、请求序号和 single-flight；只接受当前参数对应响应。对轮询采用完成后再调度或显式去重；隐藏窗口降频；错误保留最近成功数据并标记过期。

**验收**：快速切页面／模型配置后不会出现上一页数据；慢网络不会积累并行轮询；卸载组件后不更新状态。

### U03【P1／代码确认】任务状态缺少持续刷新与人类可读证据

**依据**：TaskPanel 主要在挂载和按钮操作后刷新，语音后台新建任务不一定立即出现；步骤工具名和 state 直接显示，arguments 与 evidence 主要是 JSON。

**方案**：任务事件订阅或合理轮询；用中文步骤摘要呈现目标位置、对象、变化和风险。JSON 留在展开的技术详情中。完成后给成果文件、页面、差异和核验摘要；结果未知时给真正可操作的恢复入口。

**验收**：语音创建任务无需切页即可看到；用户看得懂要改哪个文件和哪些内容；能从完成结果直接打开成果。

### U04【P1／代码确认】文字聊天输入与删除体验需要完善

**依据**：聊天用单行 input，Enter 直接发送，没有显式检查输入法 composition；删除会话没有确认，与记忆和语音删除的交互不一致；失败时通过移除最后一条消息恢复。

**方案**：使用多行输入，Enter／Shift+Enter 规则明确，组合输入结束前不发送。消息增加稳定 ID 和发送状态；失败可单条重试。不可撤销删除提供范围说明，或先归档再删除；保留忙碌期间的草稿。

**验收**：中文输入法选字不误发；发送失败只影响对应消息；长文可编辑；删除操作明确是否同时删除派生记忆。

### U05【P2／代码确认】Live2D 尺寸、输入与资源策略需要适配桌面环境

**依据**：Canvas 为 220×500，但模型缩放使用 320 和 520 的参考值；未见显示器变化和窗口缩放监听。canvas 主要依赖指针互动，缺少直接键盘操作。

**方案**：从实际可用区域计算缩放与锚点；支持不同 DPI 和显示器工作区，保存窗口位置并避免恢复到屏幕外。低电量／隐藏状态降帧，保留静态图回退。提供键盘和右键菜单等替代入口，区分拖动与点击。

**验收**：100%、150%、200% 缩放不裁切角色和字幕；跨显示器移动后清晰；隐藏时降低资源占用；模型加载失败仍能打开管理和聊天。

### U06【P2／代码确认】健康状态与开发进度需要分开展示

**依据**：AdminWindow 的模块状态为静态数组，M7 仍写待接入，而后端已有适配实现；总览主要展示模块数量而非用户当前能做什么。

**方案**：首页优先显示运行时连接、聊天模型、语音设备、游戏连接、待确认任务和最近失败。开发里程碑保留到“关于／开发状态”，由同一状态来源维护。区分已实现、已配置、已连通、实机已验收。

**验收**：未配模型时首页引导配置；插件代码存在但游戏没运行时不会写“已连接”；前后端版本与进度信息一致。

### U07【P2／工程建议】增加首次使用向导与诊断入口

**方案**：按运行时 → 聊天 → 音频设备 → 可选能力逐步设置。解释模型路由的用途与额外调用；语音服务至少提供可编辑配置入口或清晰的配置向导。缺依赖时给明确可复制命令及当前解释器路径，不要求用户自行翻源码。

**验收**：未了解项目的人可以完成基础聊天；错误密钥、缺麦克风、端口冲突和缺依赖都有对应操作；界面不以“已接入”掩盖不可用状态。

### U08【P2／工程建议】陪伴频率、提醒和可访问性作为产品设置

**方案**：提供主动问候开关、频率、安静时段、稍后提醒、已错过提醒与清理策略。喂食作为可选互动，不影响核心功能。增加焦点样式、对比度、按钮标签、缩放和屏幕阅读器验证；不要用隐藏状态文字替代所有可见反馈。

**验收**：安静时段结束后不集中倾倒大量旧进度；重要提醒可追踪；用户关闭主动互动后持续生效；纯键盘能完成设置和任务确认。

## 11. 工程质量交付与维护

### E01【P1／代码确认】公共契约应成为真正的单一来源

**依据**：packages/contracts 当前有 GameAction JSON Schema，但 Python 模型和前端类型仍手工定义。JSON Schema 要求非空 action_id/name、禁止额外字段；Python GameAction 没有完全相同约束。

**方案**：选定后端 Pydantic/OpenAPI 或独立 schema 为权威，生成 TypeScript 类型与必要的插件契约；增加协议版本、兼容范围和 fixture。游戏状态、receipt、语音事件也纳入契约。

**验收**：同一无效动作在 Python、JSON Schema 和插件边界被一致拒绝；协议变化有兼容检查；前端不再大量手写宽泛类型断言。

### E02【P1／工程建议】补上前端与跨模块集成测试

**依据**：现有测试主要集中后端，未见前端测试脚本。S05 的组件未挂载、S06 的断线丢会话均不能靠后端测试覆盖。

**方案**：为关键组件和请求状态机增加测试，再做少量高价值端到端场景：断线恢复、提醒送达、任务批准、语音打断、模型配置切换。以行为为断言，不为每个样式或纯实现细节堆测试。

**验收**：关键用户流程失败会阻止发布；测试能识别组件存在但未挂载；模拟后端验证错误和慢响应。

### E03【P1／代码确认】时序与并发测试需消除偶然性

**依据**：本次游戏测试用短 sleep 轮询，已出现全套失败而单独通过；多个服务依赖共享状态、后台任务和真实时钟。

**方案**：注入 clock、事件通知和假调度器；用 asyncio.Event／Queue 等同步条件替代等待固定毫秒。为同会话并发、重复批准、重复运行、旧连接清理和数据库竞争构造确定性测试。已存在的原子 claim_ready 测试思路继续保留。

**验收**：同一时序测试连续运行不依赖 CPU 快慢；失败日志包含顺序、session 和 seq；不要单纯加大 sleep 掩盖协议缺陷。

### E04【P1／代码确认】建立可复现依赖与构建组合

**依据**：前端与 Rust 有 lock 文件，Python 主要使用范围依赖；当前 TestClient 出现兼容弃用警告。游戏构建也依赖外部 SDK／游戏版本。

**方案**：固定经验证的 Python 运行依赖组合，开发工具另行管理；记录 Node、pnpm、Python、Rust、Java、.NET 和游戏 SDK 的支持版本。提供 clean install + lint + typecheck + test + build 的脚本或 CI，不在审查中无差别升级到最新版。

**验收**：新机器按锁定配置可复现；可选 browser/office/screen 依赖有分组验证；依赖升级附兼容测试结果。

### E05【P1／工程建议】安装包需要完整资源清单和升级策略

**依据**：当前 Tauri bundle 未体现 Python runtime 打包；persona、Live2D、GABS、插件包及外部运行库的查找路径各不相同。

**方案**：安装包 manifest 列出运行时、配置默认值、资源路径、版本和校验值；区分应用资源与用户可写数据。提供升级前检查、数据迁移与卸载数据保留选项。路径发现使用明确安装目录和资源 API，避免依赖源码目录层级。

**验收**：安装到包含中文与空格的路径可用；非管理员用户可运行；升级保留历史和配置；卸载不误删用户成果。

### E06【P2／工程建议】日志、数据和产物需要留存与清理策略

**依据**：长期使用会积累 usage、游戏动作、事件、任务 payload、浏览器 profile 和输出文件；当前未见统一容量面板与清理机制。gitignore 未明确覆盖所有 `.sqlite3` 用户自定义落盘情况。

**方案**：展示各类数据大小，按类别清理与导出；数据库清理采用事务并评估压缩；浏览器 profile 作为登录会话数据单独管理。增加防止运行时数据误入版本控制的规则和检查。清理不得默认删除用户输出成果。

**验收**：使用数月后可解释磁盘占用；一键诊断不上传用户全部数据；项目内误配置数据目录时有提示；删除范围清楚。

### E07【P2／代码确认】README 与现有实现需逐条对齐

**依据**：文档同时出现已做模型连通测试与尚无实际模型记录的陈述；桌宠文字聊天、喂食、提醒和整句语音切换描述与现有入口不一致；部分实现已显著超过 M0 骨架。

**方案**：README 聚焦启动、当前可用功能和已知限制；把历史验证记录迁到带日期的验收文档。维护功能矩阵：实现状态、配置要求、实机验证、入口位置、限制。删除已过期的时间描述，而不是不断追加新段落。

**验收**：读者按文档能找到每个承诺的入口；“可配置”“已连通”“已实测”不混用；示例端口和实际配置一致。

### E08【P2／工程建议】整理第三方资产和依赖来源清单

**依据**：项目包含 Live2D Core、Hiyori 资源、静态立绘、游戏桥接依赖及多个第三方库。当前清单中未看到集中说明来源、版本和分发条件的文件。

**方案**：建立 THIRD_PARTY_NOTICES 和资产来源清单，记录下载来源、版本、必要声明与允许的分发方式；发布前由维护者核对相关条款。静态资产校验值纳入产物清单。此项是发布准备，不是本文对授权是否合法的结论。

**验收**：每个随包分发的第三方组件都有可追溯来源；必要通知文件随安装包提供；不把来源不清的本机文件直接打入发布包。

### E09【P2／工程建议】建立真实性能基线再做优化

**方案**：在目标独显和核显设备记录启动时间、空闲 CPU/GPU、Live2D 帧率、内存、语音延迟、记忆规模、数据库锁等待、模型并发和长时间游戏日志增长。前端按需加载管理页和重资源，优先解决量测出的瓶颈。

**验收**：每项数字注明设备、数据规模和环境；不依据显卡型号推断可运行多少模型；优化有前后对照，不以重构代码量代替效果。

### E10【P2／工程建议】发布前启用并验证桌面内容安全策略

**依据**：`apps/desktop/src-tauri/tauri.conf.json` 中 csp 为 null；窗口能力包含 core:default，尚需核对实际所需权限集合。

**方案**：为本地脚本、Live2D 资源、HTTP/WebSocket 和 blob 音频制定最小 CSP；按窗口核对 Tauri 权限。避免为了让一个资源能加载而放开任意远端脚本。开发环境和发布环境可以有不同但明确的策略。

**验收**：打包后 Live2D、语音和本地 API 正常；无关远端脚本或页面不能获得桌面能力；控制台 CSP 拒绝均有解释。未启用 CSP 是加固缺口，不代表本次已发现可利用 XSS。

## 12. 建议实施顺序

### 12.1 第一阶段：先让行为和状态可信

**优先项**：S01–S03、S05–S10、S12、S14、S16；同时完成 E02、E03 中直接对应的回归测试。

**交付物**：密钥与端点绑定、普通 API 认证、参数化风险判断、提醒实际出口、聊天断线恢复、可信语音账本、游戏 sequence 和更严格结果核验。

**阶段出口**：核心功能不会因为普通断线而丢会话入口，不把未听内容记为已听，不把模型自述作为完成证据；首次全套测试失败项有确定性修复与回归。

### 12.2 第二阶段：让失败可以恢复

**优先项**：S11、S13、S15、S18、A02–A04、D01、D07、T01–T03、T08、G01–G02。

**交付物**：任务生命周期、取消与超时、启动托管、持久摘要队列、迁移与备份、文件原子提交、Office 保存证据和游戏连接恢复。

**阶段出口**：任意关键步骤被终止后，重启能看到明确状态；用户能继续、修订或放弃；恢复逻辑不会盲目重复副作用。

### 12.3 第三阶段：提高日常交互质量

**优先项**：M03–M08、D02–D06、V01–V08、U01–U08、T07、T09–T10。

**交付物**：能力探测、上下文预算、语音性能、记忆质量、统一请求层、任务实时展示、可读成果和首次使用向导。

**阶段出口**：非开发者能完成基础配置与常见任务；语音和记忆有质量指标；错误无需查源码才能理解。

### 12.4 第四阶段：逐款游戏和安装发布

**优先项**：S04、G03–G08、E01、E04–E10，必要时将 S04 提前至任何扩大骑砍自动游玩授权之前。

**交付物**：独立游戏验收记录、完整安装包、版本矩阵、资产说明、资源基线和升级演练。

**阶段出口**：在干净 Windows 环境完成安装与升级；三款游戏分别有真实闭环证据，没有通过的能力清楚标为实验性。

### 12.5 工作量如何估算

不建议将以上清单直接换算成一个保证交付日期：当前还缺真实设备、供应商、Office 和游戏测试反馈。可按单条任务先估计规模：

| 规模 | 典型内容 | 建议估算方式 |
| --- | --- | --- |
| 小 | 修正文案、恢复会话错误分支、补挂载入口 | 一个局部修改加对应回归，先做再校准团队速度 |
| 中 | 凭据绑定、语音账本、事件 ACK、sequence | 涉及前后端或状态迁移，应包含故障注入验收 |
| 大 | 动态 Agent、运行时打包、游戏恢复协议 | 拆成可独立验收的子阶段，避免以“一个功能”粗估 |
| 探索 | 真机语音、GABS 兼容、长时游戏 | 先设时间盒取得证据，再决定实现范围 |

先用第一批 5～10 个任务的实际耗时建立排期，再对余项估算。小规模维护时不要同时启动全部方向；优先串起一个完整闭环。

### 13.1 核心性能指标建议

| 指标 | 如何量测 | 首轮如何设目标 |
| --- | --- | --- |
| 冷启动可交互时间 | 启动桌面到运行时握手并能发送请求 | 先测基线，再设置目标，不用开发热启动替代 |
| 聊天首字／整句时间 | 区分检索、模型、润色与数据库耗时 | 按本地／远程路由分别记录 P50、P95 |

| 空闲占用 | CPU、内存、GPU、唤醒与轮询频率 | 桌宠显示、隐藏、后台开启分别测试 |

### 14.2 暂不建议优先做的事情

- 为追求“更强 Agent”先开放任意 shell、任意文件路径或无边界游戏动作。
- 在提醒、聊天和语音核心状态尚不可靠时，大规模扩展新游戏、新人格或更多模型供应商。

- 以“代码能运行”“插件能编译”替代可复现的日常使用验收。

本项目接下来的主要价值，是让现有能力更可信、更可恢复、更容易使用。在此基础上扩展功能，投入才不容易被反复返工抵消。
